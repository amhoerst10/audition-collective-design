# Mobile QA — 2026-09-26

Tested at 375×812 (iPhone-size) in the Claude desktop app's browser pane. Trigger: members reported trouble creating an account on mobile. Status: **findings logged, fixes not yet applied** (awaiting a live sign-up reproduction by the owner).

## Account creation (`/membership-checkout/`) — highest priority

| # | Issue | Evidence | Proposed fix |
|---|---|---|---|
| 1 | **"That username is already taken" dead end.** `simplify-signup.php` sets the username to the email's local part (before the @) and hides the username field. PMPro rejects duplicates with "That username is already taken. Please try another." — but the field is hidden, so the user can't change it. | A user `aaron` already exists, so any `aaron@…` sign-up fails. Affects desktop too; common names will collide more as membership grows. | Make the generated username unique (append a number if taken), server-side. |
| 2 | **"Are you a spammer?" from phone autofill.** PMPro's honeypot is a hidden `fullname` field; any value rejects the checkout. Mobile browsers autofill name fields aggressively, including hidden ones. | `preheaders/checkout.php` lines 336–339 and 554–555. Most likely phone-specific failure. | Clear the `fullname` value on submit (bots that don't run page scripts are still caught). |
| 3 | Password field precedes email in the DOM (only displayed in the other order). Mobile "Next" follows DOM order; iOS password manager may save the password without the email. | Field order from DOM inspection. | Move email before password in the DOM. |
| 4 | Email field has no `autocomplete="email"`, so phone keyboards/autofill don't treat it as an email field. | DOM inspection. | Add `autocomplete="email"` (and `autocapitalize="off"`). |

## Update 2026-09-28 — live mobile sign-up test

The owner created a test account (`admin@metropolitanwinds.org`) in the browser pane at 375×812 with mobile emulation, while it was monitored. **Sign-up succeeded**: redirected to the Audition Board signed in; server shows user `admin`, subscriber, membership active, email verification pending. This proves the flow works on mobile, but not that issues #1–#2 are harmless: this email's username wasn't taken and autofill wasn't used. Both remain real failure paths.

**New, most important mobile finding — Audition Board table:** the table is 1,226px wide inside a 275px scroll box. On a phone only Orchestra and City are visible; Position, Instrument and all three dates are off-screen, reachable only by an unhinted sideways swipe inside the table. Proposed fix: on narrow screens, render each listing as a stacked card (Orchestra / Position / Instrument / Deadline / Prelim / Final with labels) instead of a wide table. Filters (180–213px selects) and pagination work at this width.

Testing note: the desktop app clears an emulated phone size when Claude's turn ends. For owner-driven tests, Claude keeps its turn running (polling the page) or the owner picks **Mobile** in the pane's Viewport menu.

## Fixed 2026-09-28 (mobile-only CSS in Additional CSS, post 57; desktop verified unchanged)

- **Navigation:** the hamburger is replaced on phones (<600px) by a visible row of gold-outlined link buttons under the logo, each ≥44px tall. The owner noted the hamburger "is not really identifiable as the next place to go." Fits on one row signed in (3 links) and signed out (4 links). Resolves #6, #7, #8.
- **Audition Board:** on phones (<700px) each listing is a card: orchestra title; City/State; Position; Instrument; Deadline/Prelim/Final. Dates never wrap. The owner: "most people will be rendering via mobile." Resolves the table finding.
- **Homepage/section gap:** ~60px of empty space removed above the first section on phones. Resolves #9.
- **Contact email button:** no longer overflows; the page no longer scrolls sideways. Resolves #5.

Still open: sign-up fixes #1–#4 (username collisions, autofill honeypot, field order, email autocomplete) and #10 (eye icon color).
