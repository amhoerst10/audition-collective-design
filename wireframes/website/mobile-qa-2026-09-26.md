# Mobile QA — 2026-09-26

Tested at 375×812 (iPhone-size) in the Claude desktop app's browser pane. Trigger: members reported trouble creating an account on mobile. Status: **findings logged, fixes not yet applied** (awaiting a live sign-up reproduction by the owner).

## Account creation (`/membership-checkout/`) — highest priority

| # | Issue | Evidence | Proposed fix |
|---|---|---|---|
| 1 | **"That username is already taken" dead end.** `simplify-signup.php` sets the username to the email's local part (before the @) and hides the username field. PMPro rejects duplicates with "That username is already taken. Please try another." — but the field is hidden, so the user can't change it. | A user `aaron` already exists, so any `aaron@…` sign-up fails. Affects desktop too; common names will collide more as membership grows. | Make the generated username unique (append a number if taken), server-side. |
| 2 | **"Are you a spammer?" from phone autofill.** PMPro's honeypot is a hidden `fullname` field; any value rejects the checkout. Mobile browsers autofill name fields aggressively, including hidden ones. | `preheaders/checkout.php` lines 336–339 and 554–555. Most likely phone-specific failure. | Clear the `fullname` value on submit (bots that don't run page scripts are still caught). |
| 3 | Password field precedes email in the DOM (only displayed in the other order). Mobile "Next" follows DOM order; iOS password manager may save the password without the email. | Field order from DOM inspection. | Move email before password in the DOM. |
| 4 | Email field has no `autocomplete="email"`, so phone keyboards/autofill don't treat it as an email field. | DOM inspection. | Add `autocomplete="email"` (and `autocapitalize="off"`). |
